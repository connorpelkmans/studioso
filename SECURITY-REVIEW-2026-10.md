# Studyboard security review (October 2026, after public sign-ups)

Scope: everything in the repository, checked against the code rather than the earlier reviews (`SECURITY-REVIEW.md`, `SECURITY-AUDIT-APPSTORE.md`): the web app (`index.html`, `sw.js`), the Supabase SQL (final state after the documented run order), every Edge Function, the Cloudflare Workers, the website and email templates, the desktop app (`main.js`, `preload.js`, `lms.js`), the iOS and Android wrapper code, the CI workflows, and a secrets scan of every file and every commit.

**Result:** no Critical findings. One High (a cross-user HTML injection in Live Quiz) and a set of Medium and Low issues, all listed below. The core protections held up: row-level security on every table, no way for a user to grant themselves Pro (the plan comes from an Ed25519-signed token and server-only tables), Stripe webhook signatures, account deletion, path and IPC checks in the desktop app, and no secrets in the repository or its history (only the publishable Supabase key, which is meant to be public).

## Fixed in this pass

| # | Sev | Area | Problem | Fix |
|---|---|---|---|---|
| 1 | High | `index.html` Live Quiz | Any group member could broadcast a quiz "state" whose `i`, `n` or `counts` held HTML; it was drawn into every other member's group page unescaped. Under the site's strict CSP this allowed a full-screen fake sign-in overlay; on builds without the script hashes it was full script execution (session and AI keys). | `lqClean()` rebuilds every received state field by field: numbers forced to clamped integers, text length-capped. |
| 2 | Medium | `index.html` sign-in | Login CSRF: a link carrying someone's own `#access_token=…` signed the reader in to the sender's account. On a device used without an account, `claimDevice` then queued **all of the reader's local data** for upload into the sender's account. | `detectSessionInUrl` is now `sbUrlSessionOk()`: a session in the address is only taken when this browser asked for an email (sign-up, reset, email change) in the last 2 days, or when the device has no account and no data. Otherwise it is refused, cleared from the address, and the person is told to use the 6-digit code. Error links still pass. Test: `tests/link-safety.e2e.js`. |
| 3 | Medium | `index.html` school import | An unsigned `#sbgrab=` link from anyone could save an attacker's host as the student's Canvas site, replace the Emails inbox with fake "instructor" messages, and (for connected students) apply task changes with only an Undo toast. | A confirmation naming the source site and counts is shown before anything is saved; the inbox is stored only once the import goes ahead. `tests/lms-grab.e2e.js` covers the confirm and a cancelled forged link. |
| 4 | Medium | `index.html` AI keys | AI keys deliberately stay on the device after sign-out, but they were then used by **whichever account signed in next** (billed to the first person; with OpenAI, the next person's requests landed in the first person's logs). | Keys are tied to the account that added them (`studyboard:aiKeysOwner`); a different account signing in on the device gets them wiped. OpenAI requests now send `store: false`. |
| 5 | Low | `index.html` group files | Group file uploads were served as `data:` links with the uploader's MIME type and any file name (`.exe`, `.html`, `.lnk`…). | Always handed over as `application/octet-stream`; programs, scripts, shortcuts and HTML/SVG are refused at upload and not offered for download; control and bidi characters are stripped from names. |
| 6 | Medium | SQL `calendar_feeds` | Table-wide INSERT/UPDATE let a user write `cache_text` of any size, which the calendar-feed function then served without its ICS safety check (and could fill the database). | Column grants only (`token, user_id, options` / `options`), a 2 MB cache limit, at most 5 links per account. The function also re-checks cached text with `icsSafe` and its rate limiter now fails closed. The setup SQL embedded in the app (`CS_SQL`) is regenerated from the file. |
| 7 | Medium | SQL groups | A member removed by the owner could rejoin immediately with the unchanged invite code. | `group_bans` (server-only), recorded when the owner removes someone (not on leaving, group deletion or account deletion); `join_group` refuses with a clear message. Included in account deletion. |
| 8 | Low | SQL group tasks | `update_group_task` with `{reviewer_id: null, status: "done"}` skipped "Review before done". | Once a task has a reviewer, only that reviewer or the owner can change or clear it, and the done gate uses the existing reviewer. |
| 9 | Low | SQL devices | Updating `device_id` on an existing row dodged the free device limit and the swap log. | `device_id` and `user_id` are immutable. |
| 10 | Low | SQL misc | `push_subscriptions` not revoked from anon; one push address could belong to two accounts (one account's reminders shown on another person's device after switching); `studyboard_rate_me` accepted any name/window (unbounded rows); no daily cap on group messages; `sbg_new_code`/`sbg_lookup_ok` callable directly. | All tightened: revoke, newest owner wins per push address, only `lms-feed` with a fixed window, 500 messages a day, execute revoked. |
| 11 | Medium | Edge `calendar-sync` | A `?begin=` link made for the attacker's account and sent to a victim linked the **victim's** Google/Outlook calendar to the attacker's Studyboard account; the confirm page showed only a masked email. | The confirm page shows the full Studyboard email and warns "If someone sent you this link, close this page." (Mitigation; see follow-ups.) |
| 12 | Low | Edge functions | `error-ingest` trusted the first (client-set) `X-Forwarded-For`, so its rate limits could be dodged and crash reports flooded; billing-webhook, calendar-sync and send-reminders read unbounded bodies before auth; lms-feed redirects weren't checked against feed paths; any active Stripe subscription granted Pro regardless of price. | `cf-connecting-ip` / right-most XFF; `readLimited` everywhere; each redirect hop must be a feed URL; optional `STRIPE_PRICE_IDS` allowlist (see `PRO-PLANS-GUIDE.md`). |
| 13 | Medium | Worker `ai-trial` | One account could drain the shared daily AI pool for every student: garbled answers (forced with a tiny `maxTokens`) refunded the student's try but still charged the pool; `schema` text bypassed the input size cap; Turnstile accepted tokens without an action. | At most 3 refunds per student per day after the model ran; schema capped at 8000 characters; Turnstile requires `action === "trial"` and the Worker's hostname. The app now words the 502 message from the new `refunded` flag. |
| 14 | Low | Worker `email-capture` | A NUL byte in a header crashed the parser; crafted HTML took seconds of CPU (quadratic regex). | NULs stripped, decoding can't throw, linear patterns and a 200 KB HTML cap, parse failures bounce instead of crashing. |
| 15 | Low | Worker `key-relay` | Unauthenticated POSTs could create unlimited Durable Objects. | Per-IP rate limit binding (20/min) with a 429. |
| 16 | Medium | Desktop | Files downloaded from school sites or the cloud were saved with no Mark-of-the-Web / quarantine, so a macro `.doc` from a course opened without Protected View, and a program revealed in Explorer ran without a SmartScreen prompt. | `fs:write` marks untrusted files (Windows `Zone.Identifier`, macOS `com.apple.quarantine`); the app passes the flag for school downloads, cloud downloads, restored backups and folder backups of `Files/`; `doc`, `xls`, `ppt`, `rtf` are shown in their folder instead of opened; `:` is refused in paths on Windows so the mark can't be overwritten. |
| 17 | Low | Desktop | `app://` blocklist bypassed with `error-config.json/` or encoded `../`; CSP fell back to `'unsafe-inline'` in a packaged build with a missing hashes file; hosts-file focus block copied a user-writable file after the admin prompt (swap race); `openSafely` judged the requested name, not the symlink target; Canvas "send" had no native confirmation; `--no-sandbox` honoured in packaged builds. | All fixed (see `tests/desktop-hardening.test.js`, 50 checks). Electron bumped 44.5.1 → 44.8.0. |

## What you need to do (outside the code)

1. **Re-run the SQL** in the documented order (at least `supabase-groups.sql`, `supabase-calendar-feed.sql`, `supabase-reminders.sql`, `supabase-plans.sql`, then `supabase-lean.sql`). Every file is safe to run again; this was tested twice over on Postgres 16 with existing data, and all four self-tests pass.
2. **Redeploy** the Edge Functions `billing-webhook`, `calendar-feed`, `calendar-sync`, `error-ingest`, `lms-feed`, `send-reminders`, and the Workers `ai-trial`, `email-capture`, `key-relay` (check the `ratelimits` binding is available on your plan), then publish the site and a desktop release.
3. **Supabase dashboard:** turn on *Secure email change* and *Secure password change* (the app checks the current password itself, but a stolen token can call the API directly); turn on CAPTCHA for sign-ups; in Realtime settings turn off *Allow public access* so private channels are the only option.
4. **Before switching on the AI trial:** set the Turnstile site key and `TURNSTILE_SECRET` (it is empty in `wrangler.jsonc`, so today only a confirmed email stands between a script and the trial).
5. **Optional:** set `STRIPE_PRICE_IDS` once every live subscriber is on a current price; confirm the storage quota trigger exists (`select tgname from pg_trigger where tgrelid = 'storage.objects'::regclass`) and set a `file_size_limit` on the `studioso-files` bucket.

## Still open (not fixed here)

- **Calendar sync linking (Medium, mitigated):** the real fix is to finish the connection inside the signed-in app (the callback hands the sealed box to the app, which posts it with its own sign-in, and the function checks the uid matches). Needs testing against real Google/Microsoft sign-in and a desktop `studyboard://` route.
- **Realtime DELETE events (Medium):** Supabase sends the primary key of every deleted row in a published table to every subscriber, without RLS. For `group_members`, `items` and the other group tables that reveals user and group ids (not content) to any signed-in user. The fix is moving these tables off `postgres_changes` to private broadcast topics sent by triggers, which changes how the app listens.
- **Push tokens (Low):** someone who already has a device's FCM/APNs token can register it to their own account and send it Studyboard-branded notifications. Needs a one-time code sent to the device before a subscription is active.
- **Pro group extras (Low):** `avail`, `topics`, `gfile` items, `team_due` and reviewers are only Pro-gated in the app (no cost to you; file uploads are gated on the server).
- **Legacy 6-character invite codes (Low):** still accepted; rotate them with `new_group_code` if any exist.
- **Email capture sender (Low):** the sender shown is the email's `From:` header, which can be forged by anyone who knows the private address; the app always asks before adding. Showing it as unverified (or checking the DMARC result) needs a column for it in `capture_email`.
- **CSP `connect-src https:` (Hardening):** broad because of user-supplied calendar links and Canvas hosts; an XSS could send data anywhere. Narrow it if those fetches move server-side.
- **macOS entitlement `allow-unsigned-executable-memory`:** probably not needed by Electron 44; remove it and test a signed build.
