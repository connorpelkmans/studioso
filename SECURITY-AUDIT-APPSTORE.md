# Security audit for Apple App Store readiness (second pass)

Scope: the Electron desktop layer (`main.js`, `preload.js`, `widget-preload.js`, `widget.*`, `lms.js`, `prepare.js`, `package.json`, `build-desktop.yml`), the iOS wrapper preparation (`ios-wrapper/`), App Store review compliance, and a second look at the web page and service worker for everything touched. General web-security review (XSS, URL safety, the CSP meta tag, Supabase row-level security, secrets) is the rel-sec agent's `SECURITY-REVIEW.md`; this file does not repeat it, and lists overlaps where they matter.

**Method.** Read all desktop source and the relevant parts of `index.html` (53,000 lines, searched by feature). Everything changed was run: `node --check` on every JS file, the repo's `check.js` page check, JSON/plist validation, `package.json`'s electron-builder section against electron-builder 26.15.3's own JSON schema, a Playwright smoke of the new page UI, `supabase-moderation.sql` on a real PostgreSQL 16 (with the Supabase `auth` schema stubbed), and **the real desktop app under Electron 44.5.1** (Linux, Xcode-less) with an automated driver: window hardening, CSP header, navigation and popups, permissions, IPC checks, file access, widget, and the school sign-in windows. What cannot be checked here is listed in section 5.

**Merge note (reconciled with rel-sec, rel-polish, pro-client).** One hardened `main.js`/`lms.js`: rel-sec's sender checks, extension blocklist (`RISKY_EXT`, now checked first inside `openSafely`, so listed programs and scripts are refused and every other non-document type is only shown in its folder), `will-redirect`/`will-attach-webview` denial, permission handler and https-only school pop-ups are all kept; the stricter variants from this pass (frame-URL checks, CSP, deny-by-default list, `safeExternal`) replace the looser duplicates. `package.json` keeps rel-polish's 1.13.0, MIT, flat `node prepare.js` scripts and quoted `dist:mac-intel`, plus Electron 44, MAS and notarization config. `index.html` keeps rel-sec's CSP script and key-sync stripping, rel-polish's legal sheets and account deletion, and pro-client's `PLAN.buy`.

Severity: **High** = could lead to code execution, account takeover, secret exposure or App Store rejection with no workaround. **Medium** = real weakness or review risk with limits. **Low** = hardening. **Info** = for your awareness.

## 5. Could not be verified here

* **macOS signing, notarization and Gatekeeper**: this is a Linux container. `notarize.js` was exercised with mocked contexts (skip, required, MAS config errors) and loads `@electron/notarize`; no real signing or notarytool run happened. The electron-builder config was validated against the tool's schema, not built for macOS.
* **Mac App Store sandbox behaviour** (entitlements sufficiency, security-scoped bookmark for the chosen folder, `process.mas` paths). Test with `npm run dist:mas-dev` on a Mac.
* **Keychain-backed `safeStorage`** on macOS and Windows. On this Linux machine `safeStorage` reports unavailable and the code was verified to store nothing in that case. The adapter logic (migration, set, remove, fallback) was unit-tested with a mock.
* **iOS**: nothing was built. `native-bridge.js` and the Capacitor config were checked with mocks and JSON validation; there is no Xcode project, no TestFlight run, no push, no RevenueCat.
* **Electron 44 on macOS and Windows.** It ran correctly under Linux with the automated checks above; behaviour differences in Chromium 14x on the other systems are possible.
* **Real Supabase**: the SQL ran on PostgreSQL 16 with a stub `auth` schema, not on a Supabase project (role names `anon` and `authenticated` and `auth.uid()` were emulated). The new UI was tested against a stubbed client.
* **CDN subresource hashes** (network blocked), and `npm audit` for the web page's CDN copies.
* **Windows** installer behaviour and code signing.
